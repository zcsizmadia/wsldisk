# winget

The three manifest files winget requires, as templates. `release.yml` fills in
the version and the installer hashes at release time and opens the pull request
to [microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs).

`__VERSION__` and `__SHA256_X64__` / `__SHA256_ARM64__` are the only
placeholders; everything else is stable across releases and is reviewed here
rather than regenerated by a tool nobody reads the output of.

## Why a zip and not an installer

`wsldisk` is a single static executable with nothing to install: no registry
keys, no services, no uninstaller. winget calls that a **portable** package, and
the zip form of it is `InstallerType: zip` with `NestedInstallerType: portable`.
winget puts the executable on PATH through its links directory and removes it on
uninstall.

The alternative — shipping an MSI purely so winget has an installer to run —
would add a dependency, a build step and a way to fail, to arrive at the same
place.

## Checking a manifest by hand

These files are templates, so they cannot be validated where they sit — for two
separate reasons. `__VERSION__` is not a version and `__SHA256_X64__` is not a
hash, and `winget validate --manifest <dir>` parses *every* file in the
directory as YAML, including this README.

The filled-in manifests are what to check. `release.yml` attaches them to the
run as the `package-manifests` artifact, and validates and submits them itself;
to look at them by eye, download that artifact and:

```powershell
winget validate --manifest manifests/winget
winget install --manifest manifests/winget   # installs from the local manifest
```

`winget validate` checks the schema. Installing from the manifest checks the
things the schema cannot: that the URLs resolve, that the hashes match what is
published, and that `wsldisk.exe` is where `NestedInstallerFiles` says it is —
which is roughly what the winget-pkgs reviewer's automation checks too.

## The first submission

`release.yml` opens the pull request only when `WINGET_GITHUB_TOKEN` is set: a
classic PAT with `public_repo`, on an account that has forked winget-pkgs.
Without it the job still validates the manifests and says so in the log, and
they can be submitted by hand from the artifact — which is a reasonable way to
do the first one, since a new package identifier gets a slower human review than
a version bump.
